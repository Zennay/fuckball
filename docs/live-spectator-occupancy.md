# Live spectator-seat occupancy and invite recovery

The Custom Room host's separate spectator/bench capacity limit is useful only when it reflects the **current native roster**, not merely the count at the last socket connection. Players can move between Red/Blue team, neutral spectator and an assigned bench through existing authorized team and substitution actions without disconnecting. This product update makes the central room-roster status recompute and broadcast the actual number of neutral connected and valid reserved humans on **each** existing authoritative roster/status update. Bots never consume these slots.

The browser updates the host room-controls occupancy indicator whenever a new authenticated room roster message arrives. The displayed current used/max spectator capacity therefore follows host team moves, consented substitutions, pauses and other ordinary roster updates without extra polling traffic or a second cache. Old servers that do not advertise `spectatorLimitSupported` are unaffected; their UI never claims this feature.

When a new visitor tries to join a Custom Room whose total room is full, or whose server-side spectator/bench admission limit denies this visitor's real projected native slot, the browser now returns them to the **same invitation page** with a clear explanation instead of the general network settings. If the visitor selected explicit Watch-first, that preference is retained for retry. No room slot is allocated after a server rejection; a retry must pass the same native authorization and admission policy afresh. No secret, account token or private room access key is copied into the URL or back into the form on retry.

This feature does not bypass or modify the server-enforced admission limit, original human-only Quick Match, authorized captain/host substitutions, reconnect tickets, approved 60 Hz physics, game score, HaxLab training/replays, chat or room access key. No manual QA/test/regression suites were authored, expanded or run. Existing mandatory exact-head CI, review/branch protection and authorized VPS production deployment/drain/rollback gates remain unchanged.
